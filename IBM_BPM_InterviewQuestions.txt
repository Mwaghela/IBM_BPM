3. UCA - Under Cover Agent. 
    Used to sending and receiving a message within teamwork. The body of the message is defined by teamwork's service that is attached to the UCA

4. Event Lister. 
    Types: Start Message and Intermediate Message
    Note: Cannot be added at service layer, they are used at Business Process Layer

5. Start Message Event Lister. 
    When UCA reached to endpoint, it cause Business Process to start
    Output of UCA should be used to set the starting values of the variables within the business process
    There is no concept of co-relation in start message event because it is creating a new BPD instance & there is no data to compare it to

6. Intermediate Message Event Lister. 
    It take place while running business process
    They tell the Busienss Process to move a token forward in the process
    Intermediate Lister moves forward only if event output data matches with the co-relation data in the business process

7. Tracking. 
    To track a particular value throught the process we will use the tracking group
    To track a particular value go to Authoring Environment -> File Option -> Send to Performance Data Warehouse
    Note: not recommanded at it slow down the entire system

14. Types of Gateways.

20. Enable Javascript Debugging. 
    -> By default, IBM BPM uses compressed (minified) Dojo and Coach framework files. 
        To make these readable for debugging, you must change a setting in the WebSphere Application Server (WAS) administrative console.
        1. Log in to the WebSphere Administrative Console.
        2. Navigate to Resources > Resource Environment > Resource Environment Providers.
        3. On the Resource environment providers page, click Mashups_ConfigService.
        4. Under Additional Properties, click Custom properties.
        5. Find the property named isDebug and change its value to true.
        6. Save your changes to the master configuration and restart the application server instance.
    -> Debugging at Client Side Human Service (CSHS)
        You can insert the "debugger;" statement directly into your JavaScript code. The browser will automatically pause execution at that line if the Developer Tools are open

21. Generate unique ID for Coach View at runtime(). 
    -> Using the $$viewDOMID$$ Placeholder
        This is the standard approach for custom HTML within a Coach View. At runtime, the system automatically replaces this keyword with the unique DOM ID of the specific Coach View instance.
        Usage: In the Layout tab, add a Custom HTML control.
        Example:
            <div id="$$viewDOMID$$_myUniqueContainer">
                <input id="$$viewDOMID$$_myInputField" type="text" />
            </div>
        Benefit: It ensures all IDs are globally unique across the entire Coach, preventing element collisions.

    -> For more complex scenarios where you need a stable ID for automation (like IBM RPA) or programmatic element creation, use the controlidpath property from the Coach View context object.
        Code Snippet:
            // Inside a load or change event handler
            var uniqueID = this.context.controlidpath;
            var myElementId = uniqueID + "_customElement";
    -> Accessing the Root Element ID
        If you simply need the ID of the Coach View's wrapper <div>, you can access it directly via the DOM element in your behavior scripts.
            var viewDivId = this.context.element.id;

30. Designing Patterns used in IBM BPM / BAW
    1. Message Envelope Pattern
        Problem Statement: We have some input parameters to be passed at BPD/Service level and as project grows this parameter list will also grows and mapping this input parameters at each service is human error prone and difficult to manage.
        Solution: Message Envelope Pattern, we will wrap all the parameters and create BO as processContext and businessContext to pass is as input parameters, this will reduce human error and once variable created on top level, it will pass through all the service till down level.
BusinessContext BO will have variables like application_id, application_type, businessArea, solId, branchName etc
ProcessContext BO will have variables like instanceId, userName, userId, currentStage, startDate etc
    2. Claim Check Pattern
        Problem Statement: At BPD level, we have bulky BO coming in and out, which will create 2 problems, 1st BPD context will get bloated up because of infused variables and 2nd when you do transition from BPD to CSHS, there is deep copy serialisation and deserialisation process which is very performance intensive process.
        Solution: Claim Check Pattern recommend to pass only the application id to level services, so all details of process/business data will be stored at DB level and when we execute the service, first thing will do is to load data from DB based on application id. This way serialisation and deserialisation will be avoided as well business context will not get bloated up and you will have latest real time data available at service.
    3. Constructor Designing Pattern
        Problem Statement: When we have couple of simple of complex BO, we have different ways to initialisation, 1st we can have default value(not recommended as when signature of BO change, default value will cause issues),  2nd we can have script to initialise variables, this is also prone to errors as multiple places we have to maintain same code and can't be reused.
        Solution: Constructor Designing Pattern solves both the issues, we can have single reusable constructor service, which is responsible to construct variables, This constructor service can script, or DB retrieval or some other integration to initialise the objects
